# Student custom fields — #62 / #63

## Model and authorization

A center manager (owner or administrator) defines center-local fields with UUID keys, Arabic labels, text/number/date/select/yes-no type, position and requiredness. Registration employees enter values through their authorized student profiles; definition management never follows from registration. Definitions and values live only in the tenant database and are shared by its branches. Values cannot replace core profile columns, numbering, status or financial records.

Text keeps up to 1000 characters. Numbers are decimal strings (optional minus, up to 20 integer digits and 10 fractional digits) so JavaScript cannot round identifiers or precision. Dates use valid YYYY-MM-DD calendar dates; custom dates may be future dates. Selection lists initially contain up to 100 distinct text options. Yes/no distinguishes unfilled from explicit false; zero and false satisfy requiredness. Clearing an optional value removes the current value; omitted values preserve it. General edits, including unchanged submissions, validate current required fields; retries of an already-created request recover the original profile instead of creating another one.

Definition creation uses a stable UUID/request hash; definition edits use row revisions; profile writes use the existing profile revision plus the current definition revision. Definition/profile writes share the center lock, refresh membership/permissions at execution and commit values/profile/audit together on the tenant connection. No central/tenant atomic-write claim is made. General audit contains changed field UUIDs/counts, never custom values; definition audit records label/type/order/requiredness. Unchanged retries do not add events or revisions, and unchanged values retain timestamps.

## Forms, bounded reads and old profiles

Manager, create/edit and read-only detail use the existing shell, official shared field adapters, DataTable and native unique header form ownership. Definition pages and progressive form/detail reads contain 50 fields, with one lookahead. Initial definitions compose into the existing workspace SQL; detail values match that page. Loading subsequent existing values does not count as a user edit and never overwrites an edited value. A definition conflict preserves all input and offers current-definition loading in the header; a profile conflict explicitly reloads both the latest profile and matching first-page definitions/current template revision. Later pages can then restore their saved values without becoming blank or blocking valid saves. Recovering an already-saved creation request uses an authorized detail read for the same matching context.

Required fields added later leave existing files unchanged, with a missing-count warning. Sharing and suspension are independently executable while incomplete. This delivery's combined profile journey retains custom text, passport, manual barcode, internal number, contacts, sharing and status across general edits and browser Back. Attendance/payment/important-note interactions remain with their later owning tickets and final #82 acceptance.

The migration preserves existing profiles, requests, identities, contacts, codes and settings. It fills only a missing settings singleton, using the already-resolved center's owner email; existing settings are not overwritten. This also repairs historical centers where an absent settings row made the create form fail on null barcode settings.

## Reproduce locally

Use the disposable alpha/beta/staff fixture and proxy in `docs/student-profile-choices-acceptance.md`, after tenant migrations. From `apps/web`, set `COURSES_CUSTOM_CREDENTIALS` to the absolute mode-0600 credential file and `COURSES_CUSTOM_READ_LOG` to the proxy JSONL log including SSR reads, then run `npx playwright test student-custom-fields.spec.ts`. Optional `COURSES_CUSTOM_ORIGIN` defaults to http://alpha.courses.test:8057. The suite skips without the isolated fixture; all fixture profile values are synthetic. Run profile integration with the isolated `COURSES_PROFILE_*` connection safeguards described in `docs/student-manual-codes-acceptance.md`.


## Lifecycle, identity classification and preserved history — #63

Definitions now have an active state and general/identity classification. Disabling a field retains its values and permission classification, renders it read-only, and removes its requiredness from new/general edits. A disabled selection remains valid only as the same student's unchanged stored value: new use or returning to it after selecting another option is rejected. Managers append options or disable them instead of silently deleting their meaning. Any field that has ever stored a value keeps its type permanently; clearing a value does not make its type editable. An unused field may change type with valid new options.

Each changed value creates one tenant-local immutable version with its original field label/type, profile revision, actor/name and time. Clears have a null tombstone; retries and general edits without value changes create no duplicate versions. Existing centers import exactly one snapshot of each current value, marked as preceding version tracking, with no invented actor or earlier history. Definition changes remain in the existing safe manager audit, now showing classification, active state and disabled choices; general student audit retains field IDs/counts without values.

Identity permission and associated-branch read/manage access apply to current values and every historic version, including values written when the field was general. A grant in another branch never exposes this student's identity history. Readable identity fields render read-only when identity management is unavailable, including mixed branch grants; client validation does not ask the reader to fill these fields. General edits merge hidden stored values server-side. A missing required identity field blocks create/general edit with an Arabic request for an authorized employee, without its value; sharing and status remain independent. The creation form also restricts identity controls to its selected authorized branches. Classification or grant changes apply at the next request/execution, including a previously opened editor. No custom value expands center-wide discovery.

The profile history tab owns SSR data and reads 50 versions plus one lookahead. The layout and page share the same URL parameters and request cache key. Actual whole-page SQL after fixing a duplicate SSR read: manager 5; student new/detail/edit/history/history page two 6. The measured sample SQL time was 9.16–14.71 ms in the disposable fixture; it is a local observation, not a production estimate. Warm navigation keeps the shared frame and requests no new document. Pagination workflow links live in the shared header; DataTable owns columns, search, horizontal overflow and local pagination.
